23 · 项目实操册：两个旗舰 + 评估与安全 ​

达标目标：交付两个能扛住三十分钟追问的旗舰项目（高并发 SaaS 后端、生产级 RAG），并给 RAG 配上企业级评估体系与安全护栏。 一句话理由：项目不是「功能清单」，是「数字 + 故障 + 取舍」的证据链；面试官见过一百个 todo app，没见过一个能讲清 P99 从 800ms 优化到 120ms 的人。 衔接：20 章（排期与验收物 2/3）、06–13 章（后端全部知识在此变现）、15/16 章（RAG 链路）、21/22 章（项目二反哺两把长矛）。 ⚠️ 操练册：每节以「部署成功 / 数字入表 / 报告入库」为完成标志。

1. 项目一：高并发 SaaS 后端（第 2–6 个月） ​

一句话定位：多租户任务管理 SaaS 的后端，真实公开上线，自己运营到 50+ 活跃用户。

1.1 范围裁剪（做之前先写一页纸） ​

  • 做：注册/登录（邮箱+OAuth2 之一）、团队/租户模型、任务 CRUD、操作审计日志、webhook 出站、限流、Docker 部署
  • 不做：支付、复杂前端（拿现成 UI 模板或纯 API + 一个极简页面）、移动端
  • 裁剪原则：每个「做」都要能撑起一组面试追问；「不做」写清为什么不做（这本身就是取舍证据）

1.2 技术栈与硬指标（对齐 20 章选型） ​

  • NestJS + Prisma + PostgreSQL + Redis + BullMQ（第 22 章造完 minimq 后，可换回工业品，面试讲「造过再用，知道它为什么这么设计」）
  • Docker 多阶段构建 + GitHub Actions CI/CD + 云上单实例起步（阶段一再上不复杂的高可用，别一开始就 K8s）
  • 上线即埋：结构化日志 + 请求 traceId + Prometheus 指标 + 告警底线（对位 10 章）
  • 硬指标：公开接口 P99 < 300ms（无 AI 调用）；单位成本可计算（$/百次请求）

1.3 按周里程碑 ​

周交付章节回填
1–2项目骨架 + CI + 部署流水线跑通10
3–4认证（JWT 双 token + 刷新 + RBAC）08
5–6多租户数据模型 + 任务 CRUD + 审计09/11
7Redis 缓存层 + 限流（令牌桶）12
8–9webhook 出站队列（重试+死信+幂等）09/12
10公开上线 + 找 20 个真实用户（社群/朋友/小红书/即刻都行）—
11–12故障日：压测打出真实瓶颈 → 优化 → 复盘文档05/10/11/13

1.4 「故障日」怎么做（这是项目一的灵魂） ​

  1. 用 vegeta/k6 压到 P99 崩坏或依赖过载（连接池打满/N+1 现形/缓存击穿都行）
  2. 走完整排查：指标 → 日志 → 火焰图/慢查询 → 定位 → 修复 → 复压验证
  3. 产出 incident-report.md：时间线、根因、修复、防复发（监控项/压测纳入 CI）
  4. 面试叙事直接可用：「我排查过的生产问题」不再虚构

1.5 验收清单（全勾才算交付） ​

  • [ ] 公网地址 + 真实用户 ≥50（留存截图）
  • [ ] 三组数字：峰值 QPS、P99、单位成本（带监控截图）
  • [ ] 一份故障复盘（含前后对比数据）
  • [ ] 架构图一张（数据流 + 故障模式标注，面试白板素材）

2. 项目二：生产级 RAG 系统（第 8–15 个月） ​

一句话定位：垂直领域文档问答（选你熟的：门窗报价规则/某合规文档/开源项目 wiki），带评估报告与安全护栏，前端复用你的 4 年优势（流式 UI + 引用展示）。

2.1 范围 ​

  • 摄入：真实文档集 500+ 篇/页（自己造数据是新手项目特征），chunk 策略三档对照实验
  • 检索：pgvector 向量 + PostgreSQL FTS 关键词，RRF 混合 + rerank（bge-reranker）
  • 生成：流式 + 引用溯源 + 「不知道」兜底；结构化输出走 schema 校验
  • 服务：Python FastAPI（与 21 章 vLLM 部署对接，模型用 7B 级 + API 双轨，成本可控）
  • 评估与安全：见 2.3/2.4，这是与「demo 玩家」的分水岭，优先级高于一切新功能

2.2 里程碑（骨架期，细节随执行展开） ​

期交付
M1摄入 + 向量检索 + 生成全链路（无评估，先能用）
M2建 golden set（≥80 条，含难例）→ Recall@k / MRR / Faithfulness 基线报告
M3优化循环：chunk/混合检索/rerank 各跑一组对照，出优化前后对比图
M4Langfuse 全量 trace + 成本看板 + 语义缓存上线
M5安全：prompt 注入红队自测（2.4 清单）+ PII 脱敏 + 输出过滤，出红队报告
M620 个真实用户内测 + 一次「badcase 排障」完整复盘（面试黄金素材）

2.3 评估工程（企业级 AI 的核心壁垒位） ​

  • Golden set：80–200 条「问题 → 期望出处 → 参考答案」三层标注；从真实 badcase 持续追加（评估集是活的）
  • 检索指标：Recall@k、MRR、nDCG；每个检索改动必须跑基线（CI 里跑，对位 04 章「AI 产出要有 CI 护栏」的思路用在 AI 功能上）
  • 生成指标：Faithfulness（回答是否只基于检索内容）、Answer Relevance；LLM-as-Judge 实现 + 抽样人工校准（知道 judge 的偏差方向：位置偏好、冗长偏好、自偏好）
  • 在线评估：Langfuse trace 采样打分 + 用户反馈信号回流 golden set
  • 工具二选一实操即可：RAGAS（指标库）+ Langfuse（trace/评估运营）

必会：讲一次「指标变好但体验变差」的陷阱及校准方法；给「幻觉」下可测量的定义。

2.4 安全与护栏（对标 OWASP LLM Top 10） ​

  • 注入纵深防御（从外到内）：输入预分类 → 指令/数据分离标记 → 工具白名单 + 参数校验 → 输出过滤 → 高危动作人在环中
  • PII：摄入期 NER 识别 + 存储脱敏 + 输出期正则兜底
  • 数据投毒：文档来源分级，不可信来源进检索要打标并可被策略过滤
  • 红队自测清单：直接注入/间接注入（文档内埋指令）/越狱/工具滥用/DoS（超长上下文），每条留用例进回归集
  • 成本攻击面：语义缓存 + 用户级 token 预算 + 限流（对位 09 章）

2.5 验收清单 ​

  • [ ] 评估报告：基线 + 三轮优化前后对比（图，不是表）
  • [ ] 红队报告：5 类攻击面用例与结论
  • [ ] 成本账单：月度 token 支出 + 缓存命中率 + 单请求成本
  • [ ] 真实用户反馈记录 ≥20 条 + 一次 badcase 复盘文档
  • [ ] 前端证据：流式 + 引用 + 中断的完整体验录屏

3. 两项目共用的包装标准（D3→简历） ​

每个项目交付四件套：README（30 秒讲清定位与数字）→ 架构图（含故障模式标注）→ 复盘文档（故障/badcase 各一）→ demo 录屏（2 分钟）。写不出这四件套，等于没做完。面试叙事按 18 章 STAR 框架填，但素材全部来自上述文档，不即兴。

4. 达标标准 ​

L3：

  • [ ] 项目一验收清单全绿；能白板讲架构 + 故障定位路径
  • [ ] 项目二 M1–M4 完成，评估基线与优化对比可展示

D4：

  • [ ] 项目二评估体系 + 红队报告达到「给同行 review 不丢人」水平
  • [ ] 两项目四件套入库，且至少 1 篇项目深度文发布（素材进 24 章）
