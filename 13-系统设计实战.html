13 · 系统设计实战 ​

达标目标：L3——任何系统设计题能按五步法走完 15 分钟，经典题有完整方案。 一句话理由：系统设计题是全栈 + AI 面试的分水岭，考的是"把模糊需求变成可扩展架构"的判断力——AI 时代这道题更值钱（AI 会给方案，你要能判断）。 衔接：12 章（缓存/分布式）、09 章（API/幂等）、11 章（数据库）、15/16 章（AI）。

1. 方法论：五步法（L3 硬门槛） ​

1.1 五步框架 ​

① 澄清需求（3 分钟）—— 规模/读写比/一致性/可用性/功能范围
② 估算（2 分钟）—— QPS、存储、带宽
③ 高层设计（5 分钟）—— 画组件图：LB → 服务 → DB/缓存/MQ/CDN
④ 深入细节（3 分钟）—— 数据模型、接口、读路径/写路径
⑤ 瓶颈与扩展（2 分钟）—— 哪里先挂 → 缓存/分片/异步化

1.2 第一步的提问清单（背下来，问不完不开答） ​

- 规模：DAU 多少？读写 QPS？峰值倍数？数据总量与年增速？
- 读写比：读多写少（缓存是重点）还是写多读少（MQ 削峰/异步化）？
- 一致性：强一致（钱包/库存）还是最终一致（feed 点赞/计数可接受）？
- 可用性：能接受多少宕机？（99.9% ≈ 年宕机 8.7 小时）
- 功能范围：MVP 必须哪些、明确不做哪些（防止过度设计）

需求不同架构天差地别：同样"短网址"，100 QPS 的个人站单库单机就够，100 万 QPS 要分片 + CDN + 多级缓存。

1.3 常见扣分点（必背） ​

扣分行为正确做法
不问规模直接开答先问"QPS 多少、读多写多、一致性要求"——需求不同架构天差地别
不画图纯口述在白板/纸上画组件图，边说边画
一上来抠细节先大图后细节：高层设计完整后再深入某条路径
不提瓶颈主动说"这里会先挂，我的对策是……"
只会加缓存缓存/分片/MQ 都要能说出"解决什么、代价是什么"

必会：默写五步法各步时间分配；背澄清需求提问清单（5 问）；说出 5 个常见扣分点对应的正确做法。

2. 估算基本功（L2/L3，能算出量级） ​

2.1 常用估算公式 ​

QPS = 日请求量 / 86400 × 峰值系数（通常 3-10 倍）
存储 = 条目数 × 单条大小 × 冗余系数（约 1.5-3）
带宽 = QPS × 平均响应体大小

2.2 完整示例（短网址，背下来） ​

假设：1 亿用户、10% 日活、每人每天生成 1 条短链 + 访问 10 次

写入 QPS：1 亿 × 10% × 1 / 86400 ≈ 116/s × 峰值系数 ≈ 500/s
读取 QPS：1 亿 × 10% × 10 / 86400 ≈ 1157/s × 峰值系数 ≈ 5000/s
读:写 ≈ 10:1  → 缓存是重点
存储（1 年）：写入量 1 亿×10%×1×365 = 3.65 亿条 × 500B ≈ 18GB
带宽：读取 5000 QPS × 302 响应约 500B ≈ 2.5MB/s ≈ 20Mbps
      → 跳转后的落地页走 CDN，源站更小，单机 1Gbps 网卡远够
→ 结论：单库足够、Redis 扛读、不需要分库分片

2.3 量级参考表（背下来，估算时对号入座） ​

组件量级备注
单机 MySQL几千 QPS简单查询；写远低于读
Redis10 万 QPS单线程，别放 > 10MB 的大 key（衔接 12 章）
单机 Node几千 RPSIO 密集可更高，CPU 密集受单线程限制
Nginx / LB几万并发连接静态与入口层
CDN百万级 QPS静态资源/热点直接甩给 CDN
  • 面试点：量级对即可（±10 倍可接受），关键是"有依据 + 推导过程"

必会：背估算公式与量级参考表；独立完成短网址的 QPS/存储/带宽估算并写出推导过程。

3. 经典题详解（每题 15 分钟标准答案） ​

3.1 短网址系统（最经典，必会） ​

① 需求：生成短链、访问跳转、可过期 ② 估算：见 2.2，读远大于写 → 缓存重点 ③ 高层设计：

客户端 → LB → URL 服务（生成/跳转）
                ├→ Redis（热点映射缓存）
                └→ DB（long_url ↔ short_code，唯一约束）

④ 细节：

sql
-- 短码：随机 7 位（62 进制，0-9a-zA-Z）≈ 62^7 ≈ 3.5 万亿组合
-- 唯一约束兜底：冲突重试（幂等，衔接 09 章）
CREATE TABLE short_urls (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  short_code VARCHAR(7) UNIQUE NOT NULL,
  long_url TEXT NOT NULL,
  expires_at DATETIME NULL,
  created_at DATETIME NOT NULL,
  INDEX idx_created (created_at)
);
ts
// 读路径优先走缓存（读多写少）；miss 才查库并写回
import Fastify from 'fastify'
import Redis from 'ioredis'
import { PrismaClient } from '@prisma/client'

const app = Fastify()
const redis = new Redis()
const prisma = new PrismaClient()

const ALPHABET = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ'
function randomCode(len = 7) {
  let s = ''
  for (let i = 0; i < len; i++) s += ALPHABET[Math.floor(Math.random() * 62)]
  return s
}

// 写路径：POST /api/shorten → 随机短码 → 落库（冲突重试）→ 返回
app.post('/api/shorten', async (req, reply) => {
  const { longUrl } = req.body as { longUrl: string }
  for (let i = 0; i < 3; i++) {
    const code = randomCode()
    try {
      const row = await prisma.shortUrl.create({ data: { shortCode: code, longUrl } })
      return { code, shortUrl: `/s/${code}` }
    } catch (e: any) {
      if (e.code !== 'P2002') throw e   // P2002 = 唯一约束冲突，重试
    }
  }
  throw new Error('short code collision')
})

// 读路径：GET /s/:code → Redis → miss 查 DB → 写回 → 302
app.get('/s/:code', async (req, reply) => {
  const { code } = req.params as { code: string }
  const cached = await redis.get(`short:${code}`)
  if (cached) return reply.redirect(cached)
  const row = await prisma.shortUrl.findUnique({ where: { shortCode: code } })
  if (!row) return reply.code(404).send({ error: 'not found' })
  await redis.set(`short:${code}`, row.longUrl, 'EX', 86400)  // 缓存一天
  return reply.redirect(row.longUrl)
})

⑤ 瓶颈与扩展：

  • 读瓶颈 → Redis 缓存（命中率 90%+）+ CDN（静态跳转页）
  • 过期清理 → 惰性（访问时判断）+ 定期批量删
  • 短码用尽 → 7 位够万亿，加位即可；数据量再大 → 按 short_code 前缀分片（衔接 12 章）

3.2 Feed 流（推拉结合，L3 必会） ​

方案原理问题
推（写扩散）发布时写进所有粉丝的时间线大 V 千万粉丝 → 一次写千万条
拉（读扩散）阅读时合并关注列表的 feed读放大，热点用户查询重
推拉结合普通用户推；大 V 粉丝拉主流方案
普通用户发布 → 写进粉丝 inbox（推）
大 V 发布 → 只写大 V 的 outbox，粉丝读时拉取合并
缓存：粉丝 inbox 存 Redis List，超 800 条截断（只保留最近）
ts
// 推拉结合：发布时按粉丝数分流
const FANOUT_LIMIT = 10000   // 粉丝数阈值，大 V 判定

async function publish(userId: number, postId: number, followerIds: number[]) {
  if (followerIds.length <= FANOUT_LIMIT) {
    // 普通用户：写扩散，逐个粉丝 inbox
    const pipe = redis.multi()
    for (const fid of followerIds) {
      pipe.lpush(`inbox:${fid}`, postId)
      pipe.ltrim(`inbox:${fid}`, 0, 799)   // 只留最近 800 条
    }
    await pipe.exec()
  } else {
    // 大 V：写扩散一次就是灾难，只写 outbox，粉丝读时拉
    await redis.lpush(`outbox:${userId}`, postId)
  }
}

// 读时间线：自己 inbox + 关注的大 V outbox 合并排序
async function timeline(userId: number) {
  const mine = await redis.lrange(`inbox:${userId}`, 0, 199)
  const bigVs = await redis.smembers(`following_bigv:${userId}`)
  const pulls = await Promise.all(
    bigVs.map((v) => redis.lrange(`outbox:${v}`, 0, 49))
  )
  return [...mine, ...pulls.flat()]
    .sort((a, b) => b - a)          // 按 postId 倒序（或时间戳）
    .slice(0, 200)
}
  • 面试点：能说出"推拉结合阈值怎么定"（看粉丝数分布）+ 各自代价

3.3 限流器系统（衔接 09 章，分布式版） ​

单机：令牌桶（内存）
分布式：Redis INCR + Lua 脚本（原子，多实例共享计数）
架构：网关层（Nginx/API Gateway）按 IP/用户限流 → 业务层兜底
数据：redis 计数 key（rate:{id}:{window}），滑动窗口用 zset
lua
-- Redis Lua 脚本：固定窗口限流（原子执行，多实例共享）
-- KEYS[1] = rate:{id}:{window}，ARGV[1] = 上限，ARGV[2] = 窗口秒数
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[2])
end
if current > tonumber(ARGV[1]) then
  return 0    -- 拒绝
end
return 1      -- 放行
ts
// Fastify 里挂 preHandler 钩子（衔接 07 章钩子）
import { createClient } from 'redis'
const redis = createClient()

app.addHook('preHandler', async (req, reply) => {
  const window = Math.floor(Date.now() / 60_000)          // 每分钟一个窗口
  const key = `rate:${req.ip}:${window}`
  const ok = await redis.eval(RATE_SCRIPT, {
    keys: [key], arguments: ['10', '60'],                 // 每 IP 每分钟 10 次
  })
  if (!ok) return reply.code(429).send({ error: 'too many requests' })
})
  • 面试点：能说"限流要在网关做一层 + 业务做一层"（纵深）；滑动窗口更平滑但成本更高

3.4 AI 问答产品（全栈 + AI 王炸题，务必练熟） ​

① 需求：基于个人知识库的问答（RAG）、流式回答、成本可控 ② 估算：QPS（低，个人站）→ 重点是成本与延迟不是并发 ③ 高层设计：

用户 → Web(SSE 流式) → AI 网关 → 检索服务 → 向量库/全文库
                        └→ LLM API（厂商）→ 流式回传
缓存：问题哈希命中 → 直接回（省 token）
降级：LLM 挂 → 提示稍后 / 简化模型 / 本地模型兜底

④ 细节（衔接 15/16 章）：

ts
// 成本控制第一招：相同问题缓存（问答场景重复率可观）
import { createHash } from 'node:crypto'

app.post('/api/ask', async (req, reply) => {
  const { question } = req.body as { question: string }
  const hash = createHash('sha256').update(question).digest('hex').slice(0, 32)
  const cached = await redis.get(`qa:${hash}`)
  if (cached) return { answer: cached, from: 'cache' }   // 命中：零 token 成本
  const answer = await runRag(question)                   // 检索 + 拼 prompt + 调 LLM
  await redis.set(`qa:${hash}`, answer, 'EX', 3600)
  return { answer, from: 'llm' }
})
  • 成本控制：prompt 缓存、相同问题缓存、token 预算上限（max_tokens 封顶）
  • 降级路径：LLM 不可用 → 返回检索结果摘要（不空手）；简化模型兜底（衔接 15 章）
  • 可观测：每次调用记录 token/耗时/成功（衔接 06 章网关思路）——"一次线上事故 = 一次 token 账单事故"

⑤ 瓶颈：LLM 延迟是瓶颈 → 流式 + 首 token 优化；成本是瓶颈 → 缓存 + 预算；并发是瓶颈 → 检索与生成拆成独立服务弹性扩

3.5 知识库搜索（企业级案例，可延伸） ​

数据量小时 MySQL FULLTEXT 就够，别急着上 ES：

sql
ALTER TABLE docs ADD FULLTEXT INDEX ft_title_content (title, content);

-- 关键词检索：按相关度排序
SELECT id, title, MATCH(title, content) AS score
FROM docs
WHERE MATCH(title, content) AGAINST ('缓存穿透' IN NATURAL LANGUAGE MODE)
ORDER BY score DESC
LIMIT 20;
→ 热词结果缓存（Redis，衔接 12 章）
→ 数据量大 / 多语言 / 需要语义 → 上 Elasticsearch（全文）或向量检索（RAG 接入点，衔接 15 章）
→ 混合检索 + rerank：FTS 与向量结果用 RRF 合并（衔接 15 章）

必会：15 分钟内完整走完短网址/Feed 流/限流器/AI 问答中任一题（澄清→估算→大图→细节→瓶颈）；能写出 Redis 限流 Lua 与短网址读路径代码；能说出 Feed 推拉结合的阈值逻辑。
