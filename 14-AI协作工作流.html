14 · AI 协作工作流（vibe coding） ​

达标目标：方法论到 L2，实战到 L3。 全程贯穿，是所有工程章节的"生产方式"。 一句话理由：AI 时代效率差距不在"会不会问"，而在"会不会喂上下文、会不会验收"。会写的人 + AI = 倍增；不会验收的人 + AI = 在错误方向上加速。 衔接：04 章（CI/工程化关卡）、15/16 章（AI 工程落地）；本学习站根目录 AGENTS.md 就是"给 AI 的项目宪法"完整范式。

1. 工具与工作区（L2） ​

1.1 主力工具选一个精 ​

工具形态强项
Claude CodeCLI（终端）贴近工程：读仓库/改文件/跑命令/hooks/subagents；适合大任务与自动化
CursorIDEdiff 式补全、多文件编辑可视化；适合日常写代码
Copilot 类IDE 内嵌补全最快；代理能力弱
  • 能力边界：这些工具能读仓库、改文件、跑命令、调工具；但不知道你的意图和验收标准——这两样必须由你提供
  • 选型：重重构/跨文件任务 → CLI 代理；日常编码 → IDE；核心是"你会不会用它"，不是用哪个
  • 工作区纪律：每个项目一份 AGENTS.md，AI 一进仓库先读它——比每次口头叮嘱可靠一百倍

1.2 读一遍本学习站 AGENTS.md（L2 必做） ​

它是"给 AI 的站内权威说明"完整范式：项目概述 / 架构 / 命令 / 关键约定 / 开发流程。逐行理解每条存在的理由——每条约定都是在回答"AI 最容易在这错什么"。

必会：讲主力工具能力边界；能解释 AGENTS.md 每条约定对 AI 的意义（如"禁止 import reka-ui"防 AI 引入第二套 UI 库）。

2. 上下文工程（L2 硬门槛，比 prompt 更重要） ​

2.1 先喂背景再派活 ​

❌ "帮我加个导出按钮"（AI 不知道项目结构/约定/风格）
✅ "项目是 Vue3+TS monorepo（pnpm workspace），UI 用 @/components/ui，
    新工具按 apps/web/src/features/tools/xxxTool.vue 建并在
    apps/web/src/data/tools.ts 注册。请先读这两个文件，然后给"导出按钮"的实现计划。"
  • 让 AI 先读 README / AGENTS / 目录结构 / 相关文件，再开始改——一次说清背景，胜过五轮返工

任务描述模板（复制即用）：

markdown
### 背景
- 项目：Vue3 + TS monorepo（pnpm workspace），UI 统一用 @/components/ui
- 相关文件：apps/web/src/features/tools/xxxTool.vue（已有 N 个同类工具可参考）
- 约定：不新增依赖；代码风格见 .editorconfig
### 任务
在 xxxTool.vue 增加"导出 CSV"：本地生成 CSV 并触发下载
### 要求
- 不引入新依赖（用 Blob + URL.createObjectURL）
- 表头与列顺序以 data/tools.ts 的字段定义为准
- 先读以上文件再动手；先给实现计划等我确认

2.2 报错三件套（一次给全） ​

报错原文（完整堆栈，别截图截一半）
+ 相关代码（出错函数 + 调用处）
+ 复现步骤（怎么触发、期望 vs 实际）
  • 给全三件套，AI 一次定位；缺一个它就开始猜，来回浪费

2.3 约定写进文件，不靠嘴说 ​

  • 项目级约定沉淀为 AGENTS.md/CLAUDE.md——文件是持久记忆，对话不是
  • 本学习站用硬链接保持两份同步（cmd /c mklink /H CLAUDE.md AGENTS.md）——一处修改处处生效，避免两份漂移
  • 面试点：能讲"为什么要文件化约定而不是每次靠提示词"（一致性 + 新人/AI 都能读到）

2.4 plan-first（L2 习惯） ​

  • 多文件改动前，先让 AI 输出"改动计划"让你确认，再开写
  • 计划要含：改哪些文件、每个文件改什么、影响面、怎么验证——确认了再动手，避免方向错
markdown
AI 的"改动计划"应该长这样（你确认后才准动手）：
- 文件 1：xxxTool.vue —— 新增 exportCsv() + 导出按钮
- 文件 2：data/tools.ts —— 无改动（字段已够）
- 影响面：仅工具页，无全局状态变更
- 验证：pnpm --filter web build + 手动点一次导出

必会：默写"先喂背景"的任务描述模板；讲报错三件套；讲硬链接同步 AGENTS/CLAUDE 的用意；说清 plan-first 计划要含哪四要素。

3. Spec-driven 开发（L3） ​

3.1 流程（用本学习站跑一个真实需求） ​

需求 → 验收标准（acceptance criteria）→ 拆小步 → 每步可验证可回滚
markdown
## 需求：新增"汇率换算"工具
## 验收标准
- [ ] /tools/currency-converter 可访问（需登录）
- [ ] 输入金额+币种 → 显示换算结果（本地计算，无网络请求）
- [ ] 组件注册进 toolMetaMap，卡片显示正确
- [ ] pnpm --filter web build 通过
  • 每步"算成功"要可机器验证：能跑、测试过、类型/lint 通过、符合仓库约定
  • 让 AI 先写测试再写实现（TDD + AI）：测试即行为护栏，先定"什么是对"再写代码
  • 小步提交：AI 一次改太多文件时喊停，要求拆开（diff 太大无法审）

拆步示例（汇率换算工具）：

① 写 spec + 验收标准（机器可验证）
② 先写路由/组件骨架 + 空状态测试
③ 实现换算逻辑 + 单测（含非法输入：负数/非数字）
④ UI 接入 + 集成走查
每步独立提交；第 ③ 步出问题时只回滚它，不影响 ①②

必会：写一个带验收标准的 spec；讲"先测试后实现"；讲小步提交；能演示把一个需求拆成 4 个可验证的小步。

4. 审查 AI 产出（L3 核心能力） ​

AI 代码默认"能跑但不一定对"，必须过四关：

mermaid
AI 产出 → ① 机器关（类型/lint/构建/测试）
        → ② 行为关（手动走关键路径 + 边界）
        → ③ diff 关（逐行读改动）
        → ④ 最坏情况关（线上最坏会怎样）
        → 合并
  1. 机器关：类型检查 / lint / 构建 / 测试全绿（没 CI 就先本地跑）——机器能兜的先让机器兜
  2. 行为关：手动走一遍关键路径，尤其是边界与异常分支（空数据、超时、权限不足）
  3. diff 关：逐行读改动——命名、错误处理、是否引入新依赖（一个"小改动"塞进新依赖 = 风险）、是否动了不该动的文件
  4. 最坏情况关：问自己"这段代码在线上最坏会怎样"（超时、并发、脏数据、权限绕过）

AI 三大高频安全坑（审查时重点盯）：

ts
// ① 越权：AI 只在页面层判断角色，接口层没校验
//    ❌ app.get('/api/admin/stats', ...) 没查 token 角色
//    ✅ 服务端从 token 取 userId + 角色校验（衔接 08 章）
// ② 注入：把用户输入直接拼进 SQL / 查询
//    ❌ `SELECT ... WHERE user = ${req.query.userId}`
//    ✅ 参数化查询 / Prisma 的 where
// ③ XSS：把 LLM 返回的 HTML 直接 v-html / innerHTML
//    ✅ 转义或只允许白名单标签

面试讲项目时，"我审出了 AI 写的 XX 问题并修掉"是极有说服力的案例——提前积累 2-3 个真实案例。

必会：背四关；讲"为什么机器关要最先"；能举一个自己审出 AI 问题的例子（越权/注入/XSS 三选一）。

5. 进阶：把 AI 用成团队（L3） ​

5.1 角色分工 ​

角色用法注意
结对者你定方案它实现方案必须你定（AI 默认方案平庸）
审查者它找 bug 你判断判断权在你（AI 审查也会误报）
解释者读不懂的代码让它讲顺带学别人的代码
写手文档/注释/测试样板别让它写"有观点"的内容（它会端水）

5.2 并行子任务 ​

  • 拆成相互独立的子任务并行推进（AI 是廉价劳动力）
  • 合并时严格过四关——并行越快，审查越要严
  • 前提：任务真的独立（共享文件的任务并行 = 冲突地狱）

5.3 给 AI 建"记忆" ​

  • 踩过的坑写进约定文件，让它下次不犯——本学习站 AGENTS.md 就是这样演进的
  • 每次"AI 犯错"都值得沉淀一条：## 关键约定 里加一行，比下次骂它有用
  • 闭环：踩坑 → 沉淀约定 → AI 不再犯（这是"AI 团队"唯一能复利的机制）

5.4 识别 AI 盲区（重点盯） ​

  • 依赖版本（AI 爱用"最新"或过时版本）
  • 跨模块耦合（AI 只看到当前文件，改了 A 不知道影响 B）
  • 业务语义（AI 不知道"为什么这个字段必须唯一"）
  • 安全边界（AI 生成的代码默认不带鉴权/校验）

5.5 AI 产出 → CI 关卡（把审查自动化） ​

yaml
# AI 产出 → CI 关卡（衔接 04 章）：机器关全自动，人只审机器兜不住的
name: ai-guard
on: [pull_request]
jobs:
  guard:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm i -g pnpm@11
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint          # 机器关①：风格 + 简单规则
      - run: pnpm typecheck     # 机器关②：类型（AI 最爱漏的类型错误）
      - run: pnpm test          # 机器关③：行为护栏
      - run: pnpm build         # 机器关④：构建产物可出
      # ⑤ 依赖变更审查：diff 里新增 dependencies 必须人工 review

必会：讲四个角色分工；讲并行子任务的前提与风险；讲"踩坑 → 沉淀约定 → AI 不再犯"闭环；能画出"AI 产出 → CI 关卡"流水线并说明每关防什么。

6. 常见坑（每条都是真实事故） ​

坑对策
让 AI 一次重构大文件 → diff 无法审 → 回滚成本高小步提交，diff 太大喊停
没有验收标准让它"自由发挥" → 方向错了还自我感觉良好先写 spec + 可机器验证的验收标准
项目无测试就让 AI 猛写 → 行为无护栏，越改越错先让 AI 补测试骨架，再让它写实现
把密钥/数据喂给第三方工具 → 权限边界失控密钥走环境变量，不经对话/工具
让 AI 直接动生产数据 / 发外部请求 → 高危操作必须人确认（衔接 16/17 章）高危操作默认拒绝 + 人确认

7. 面试高频题速答 ​

题速答要点
上下文工程是什么先喂背景（README/AGENTS/结构）+ 报错三件套 + 约定写进文件
为什么约定要文件化对话是临时的，AGENTS.md 是持久记忆，一致性
AGENTS.md 写什么概述/架构/命令/约定/坑——每条回答"AI 最容易错什么"
怎么让 AI 一次做对plan-first + 验收标准 + 先测试后实现
审查 AI 代码四关机器/行为/diff/最坏情况
为什么小步提交diff 太大无法审，回滚成本高
怎么防 AI 引入新依赖diff 关专门看 dependencies + CI 依赖变更审查
AI 代码高频安全坑越权/注入/XSS——服务端校验 + 参数化 + 转义
面试怎么讲 AI 实践"我审出了 AI 的 XX 问题并修掉" + 量化

8. 达标标准 ​

L2：

  • [ ] 能写一份 5 行内的"背景 + 任务"描述，让 AI 一次做对
  • [ ] 能解释 AGENTS.md 每条约定对 AI 的意义

L3：

  • [ ] 用本学习站跑通完整需求：plan → 实现 → 测试 → 审查 → 合并，审出至少 1 处 AI 问题
  • [ ] 维护一份 AGENTS.md，演示"踩坑 → 更新约定 → AI 不再犯"
  • [ ] 设计"AI 产出 → CI 关卡"流水线（类型/lint/测试/构建 + 依赖审查），说明每关防什么
