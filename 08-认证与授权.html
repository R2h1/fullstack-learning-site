08 · 认证与授权 ​

达标目标：L2 硬门槛——JWT 全流程、Cookie 安全、授权模型能讲透；L3——双 token 落地与安全审查。 一句话理由：认证是"我怎么知道你是谁"，授权是"你能干什么"——全栈面试必考，也是 AI 最容易写错安全边界的地方。 对照生产级实现：plugins/auth.ts + auth-middleware.ts + ResourcePermission（企业级认证授权范本）。

1. 认证基石：Session vs Token（L2） ​

1.1 两种模型对比 ​

SessionJWT（无状态 token）
存储服务端（内存/Redis）客户端持有，服务端不存
撤销可主动踢下线（删 session）不可主动撤销（只能等过期）
水平扩展需共享 session 存储（Redis）天然无状态可扩展
泄密影响服务端可控泄漏即伪造凭证（要短过期）
性能每次查存储验签即可（CPU 便宜）

1.2 选型判断（能说 trade-off） ​

  • 要"踢人下线/多端互踢/实时封禁" → session（或 JWT + refresh 服务端存储）
  • 要无状态扩展、微服务共享 → JWT
  • 面试回答：不要二选一，说"JWT 无状态是优点也是缺点——不可撤销，所以生产通常配 access + refresh 双 token，refresh 可撤销"

必会：讲对比表；说"JWT 不可撤销"带来的问题与解法。

2. JWT 深度（L2 硬门槛） ​

2.1 结构：三部分 ​

header.payload.signature
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwicm9sZSI6InVzZXIifQ.s0meS1gnAturE
└──── header ────┘ └──── payload ────┘ └──── signature ────┘
  • header：{ "alg": "HS256", "typ": "JWT" }
  • payload：标准字段（sub/iat/exp/iss/aud）+ 业务字段（如 role）
  • signature：HMAC(header.payload, secret)——防篡改的关键

2.2 为什么能防篡改（L2 必答） ​

攻击者改 payload 里的 role: user → super_admin
→ signature 不匹配（他没密钥）→ 验签失败 → 拒绝
  • 关键认知：payload 只是 Base64Url 编码，不是加密——任何人可解码看到内容，所以绝不放密码/手机号等敏感信息
  • HS256 vs RS256：
HS256RS256
密钥对称（同一密钥签验）非对称（私钥签、公钥验）
适用单服务内部多服务/第三方校验
风险密钥泄漏=全被伪造公钥可分发，安全

2.3 双 token 完整实现（L3 必会） ​

ts
// 登录：签发 access + refresh
function issueTokens(user) {
  const access = jwt.sign({ sub: user.id, role: user.role }, SECRET, { expiresIn: '15m' })
  const refresh = jwt.sign({ sub: user.id, type: 'refresh' }, REFRESH_SECRET, { expiresIn: '7d' })
  return { access, refresh }
}

// refresh 换新 access（refresh 可撤销：存服务端/黑名单）
async function refreshAccess(refreshToken) {
  const payload = jwt.verify(refreshToken, REFRESH_SECRET)
  const saved = await redis.get(`refresh:${payload.sub}`)   // 撤销检查
  if (saved !== refreshToken) throw new Error('refresh 已失效')
  return issueTokens(findUser(payload.sub))
}

// 踢人下线：删掉 redis 里的 refresh 记录即可
await redis.del(`refresh:${userId}`)
  • 为什么 access 短：泄漏损失小；为什么 refresh 长：用户不用反复登录
  • refresh 的存储：HttpOnly Cookie（防 XSS 窃取）；access 放内存（刷新页面丢失可接受，用 refresh 换）

必会：讲三部分结构 + 防篡改原理；写双 token 签发/刷新/撤销代码；说"为什么 payload 不能放敏感信息"。

3. Cookie 安全四件套（L2 必答） ​

属性值防什么
HttpOnlytrue防 XSS 用 JS 读 token（document.cookie 拿不到）
Securetrue仅 HTTPS 传输（防抓包）
SameSiteStrict/Lax防 CSRF（跨站请求不自动携带）
Max-Age7d 等生命周期控制
ts
// 生产模式：签名 cookie + JWT 从 cookie 读
reply.setCookie('token', accessToken, {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax',
  maxAge: 7 * 24 * 3600,
  path: '/',
})
  • SameSite 三档：Strict（同站才带）/ Lax（顶层导航可带，默认安全）/ None（跨站都带，必须配 Secure）
  • 面试点：XSS 偷 cookie → HttpOnly 挡；CSRF 借 cookie → SameSite 挡；两者分工不同

必会：背四件套各防什么；写 setCookie 完整参数；讲 SameSite 三档。

4. 密码存储与登录防护（L3） ​

4.1 为什么 bcrypt（L2 必答） ​

  • MD5/SHA 直接存：无盐 → 彩虹表秒破；有盐但快 → 可暴力穷举
  • bcrypt 慢哈希 + 内置盐：bcrypt.hash(password, cost)，cost=10 约 100ms——攻击者同样要付出百倍成本
  • 生产规范：cost 取 10-12（平衡）；新用户统一 hash 再存；绝不存明文
ts
import bcrypt from 'bcryptjs'

const hash = await bcrypt.hash(password, 10)        // 注册
const ok = await bcrypt.compare(password, hash)     // 登录（常数时间比较）
if (!ok) return reply.code(401).send({ error: '用户名或密码错误' })

4.2 登录防护（L3） ​

  • 限流：按 IP + 按用户名计数（Redis INCR + 过期）；连续失败锁定 N 分钟
  • 统一错误信息：登录失败提示"用户名或密码错误"（不暴露"用户不存在"）
  • 其他：验证码/滑块（可选）、login 接口也要限流（别只限注册）

必会：讲 bcrypt 为什么（慢哈希+盐）；写登录防护（限流 + 统一错误）。

5. 授权模型（L2/L3，对照生产实现） ​

5.1 RBAC（角色） ​

  • 用户 → 角色（user / super_admin）→ 权限；够用为主
  • 生产项目 User.role 字段即 RBAC 的简单实现

5.2 资源级权限（生产实例） ​

  • ResourcePermission：{ type: 'tool'|'knowledge', key: 'bmi-calculator', access: 'public'|'admin_only' }
  • 场景：某个工具/知识条目只对超管可见——权限粒度到资源，不是到角色

5.3 超管校验为什么实时查库（L2 能讲 trade-off） ​

ts
// 生产 auth-middleware.ts 的做法：JWT 只存 userId，每次查库比对 role
async function requireSuperAdmin(request, reply) {
  await request.jwtVerify()                                   // 401
  const user = await prisma.user.findUnique({
    where: { id: request.user.userId },
    select: { role: true },
  })
  if (!user || user.role !== 'super_admin') {
    return reply.status(403).send({ error: '需要超级管理员权限' })
  }
}
  • 为什么实时查库：JWT 里存的 role 在有效期内不变——如果管理员被降级，旧 token 还能继续用旧权限。实时查库牺牲一次查询，换权限实时性
  • 面试点：能说出这个 trade-off 就是加分（很多人只会"JWT 存 role"）

必会：讲 RBAC vs 资源级权限；写 requireSuperAdmin 并解释为什么实时查库。

6. OAuth2（加分项，能讲 Authorization Code + PKCE） ​

6.1 Authorization Code 流程 ​

① 用户点"微信登录" → 跳第三方授权页
② 用户授权 → 回调到你的后端，带授权码 code（带 state 防 CSRF）
③ 后端拿 code + client_secret 换 access_token（后端到后端，前端看不到 token）
④ 用 token 调用户信息接口 → 建本地会话/JWT

6.2 为什么 code 换 token 必须后端做 ​

  • token 是长期凭证，放前端 = 被 XSS 窃取；code 一次性 + 短时，只换一次
  • PKCE（移动端/SPA）：前端生成 code_verifier，换 token 时带 code_challenge——即使 code 被截获也无法换 token
  • 与 JWT 关系：OAuth2 解决"第三方授权"，登录后你的系统内部继续用 session/JWT 管会话

必会：画 Authorization Code 流程；讲"code 换 token 为什么在后端" + PKCE。

7. 认证安全审查清单（L3，审 AI 代码用） ​

  • [ ] token 存在哪？（HttpOnly Cookie / 内存，别放 localStorage 明文）
  • [ ] access 过期时间？（太长 = 泄漏损失大）
  • [ ] refresh 能不能撤销？（服务端存/黑名单）
  • [ ] payload 里有没有敏感信息？（密码/手机号禁止）
  • [ ] 登录有没有限流 + 统一错误提示？
  • [ ] 密码是不是 bcrypt（别 MD5/SHA）？
  • [ ] 角色校验是实时查库还是信任 JWT 载荷？
  • [ ] CSRF 防护（SameSite）和 XSS 防护（HttpOnly）都配了？

8. 面试高频题速答 ​

题速答要点
session vs JWT可撤销 vs 无状态；要踢人用 session/refresh
JWT 为什么能防篡改signature 用服务端密钥签，改 payload 验签失败
payload 为什么不能放密码Base64 不是加密，任何人都能解码
为什么需要 refresh tokenaccess 短防泄漏 + refresh 可撤销，兼顾安全与体验
踢人下线怎么做refresh 存服务端/黑名单，删记录即失效
Cookie 四件套HttpOnly 防 XSS / Secure 仅 HTTPS / SameSite 防 CSRF / Max-Age
密码为什么 bcrypt加盐 + 慢哈希，抗彩虹表与爆破
超管为什么实时查库防 JWT 有效期内角色变更后权限陈旧
OAuth2 code 为什么后端换token 不透前端防窃取；PKCE 防 code 被截获
JWT 存哪最安全HttpOnly Cookie；localStorage 会被 XSS 读
