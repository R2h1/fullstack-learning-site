04 · 前端工程化 ​

达标目标：L3 硬门槛（工程章节按生产级要求）。 一句话理由：AI 生成代码很容易，让它"能跑、能测、能部署、能协作"是工程化的事——这是把 AI 产出变成线上产品的流水线。 示例项目是一套完整教材：Vite 8/rolldown、pnpm workspace、turbo、GitHub Actions、AGENTS.md。学完本章，你能"抄着配"而不是"听着懂"。

1. 模块系统深度 ​

1.1 ESM 的三阶段加载（L2 进阶） ​

ESM 加载分三个阶段（与 CJS 的本质差异）：

① 解析（Parse）—— 静态扫描 import，构建模块依赖图（不执行）
② 实例化（Instantiate）—— 为所有模块创建绑定（live bindings）
③ 求值（Evaluate）—— 按依赖顺序执行模块体
  • live bindings：ESM 的 import 是"活的绑定"，导入方看到导出方的实时值（不是拷贝）；CJS 的 require 是运行时拷贝快照
  • 循环依赖：CJS 遇循环拿到"未完成的 exports"（可能 undefined）；ESM 因绑定先行，只要不在求值前读取也安全
js
// ESM 循环依赖安全示例（a.js）
import { b } from './b.js'
export const a = 'a'
console.log(b) // 'b' —— 绑定已建立，求值顺序保证读到值

// CJS 循环依赖（a.js）
const b = require('./b')
module.exports = { a: 'a' }
console.log(b) // 可能 undefined —— require 时 b.js 还没完成导出

1.2 打包器全景（能说清定位差异即 L2） ​

工具定位特点
Webpack全能打包器生态大、配置重、慢
Vite（dev）原生 ESM + 依赖预构建不打包源码，快
Rollup库/生产打包tree-shaking 最强，ESM 优先
esbuild极速转译/打包Go 写的，快百倍级；功能少
RolldownRollup 的 Rust 重写Vite 8 已用，速度与 tree-shaking 兼得
TurbopackWebpack 的 Rust 继任Next.js 默认

判断口诀：dev 用"不打包"的（Vite），生产用"静态分析强"的（Rollup/Rolldown），老项目才被迫用 Webpack。

1.3 tree-shaking 生效条件（L3 必答） ​

  1. 源码用 ESM 导出（静态可分析）
  2. 库声明 "sideEffects": false（或 sideEffects: ["*.css"]）——否则打包器保守保留可能有副作用的模块
  3. 不通过"副作用写法"引入（import './polyfill' 是刻意保留的副作用，要写明）

必会：讲 ESM 三阶段 + live bindings + 循环依赖差异；说清打包器定位矩阵；答 tree-shaking 三个条件。

2. 构建与代码分割（L3 核心决策） ​

2.1 Vite 架构（示例项目在用） ​

环境机制为什么快
dev原生 ESM 按需加载 + 依赖预构建（esbuild 把 CJS 依赖转 ESM 并缓存到 node_modules/.vite）源码零打包，改哪热更哪
buildRollup/Rolldown 打包 + 代码分割 + 压缩生产级产物
  • env 变量：.env.* + import.meta.env；VITE_ 前缀才暴露给前端（密钥只放后端）
  • proxy：dev 代理 /api → 后端，避免 CORS（生产 vite.config 常见配置）
  • 别名：@/* → src/*

2.2 代码分割配置（能抄的示例） ​

ts
// vite.config.ts —— manualChunks 示例
export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          vue: ['vue', 'vue-router', 'pinia'],   // 稳定大依赖单独成 chunk，长期缓存
          vendor: ['axios'],                      // 其余第三方
        },
      },
    },
  },
})
  • 路由懒加载（框架层）：component: () => import('@/views/xxx.vue')——自动切 chunk
  • 决策流程：路由懒加载 → 大依赖单独 vendor → 用体积报告（rollup-plugin-visualizer）看结果 → 超预算才拆业务 chunk
  • 坑（真实生产案例）：错误分包让首页预载过大——某项目 commit 里"首页预载 3.4MB TS 编译器"就是把应按需加载的 TS 编译器错合进首屏 vendor chunk，最终回滚默认分包。trade-off：大依赖单独缓存（业务更新不失效）vs 首屏体积膨胀 + chunk 请求数变多

必会：写一份 manualChunks；讲清"懒加载哪些、vendor 怎么分"的决策与 trade-off。

3. 测试体系（L3） ​

3.1 金字塔与工具 ​

e2e（Playwright）        —— 少而关键：登录、下单、搜索
组件测试（VTU/Testing Library）—— 交互与渲染
单测（Vitest）           —— 多而快：纯逻辑/工具函数
  • Vitest vs Jest：Vitest 基于 Vite（快、ESM 原生、TS 免配）；Jest 生态老但配置重
  • 测试替身三件套（能写出来）：
ts
// 单测示例（Vitest）—— 替身三件套
import { describe, it, expect, vi } from 'vitest'

// mock：替换整个实现（如外部 API）
vi.mock('@/api/knowledge', () => ({ fetchList: vi.fn() }))

// stub：只返回预设值
const getDiscount = vi.fn().mockReturnValue(0.9)

// spy：记录调用（测"交互发生过"）
const onSave = vi.fn()
button.click()
expect(onSave).toHaveBeenCalledTimes(1)
expect(onSave).toHaveBeenCalledWith({ id: 1 })
ts
// 组件测试示例（Vue Test Utils）
import { mount } from '@vue/test-utils'
import ToolCard from '@/components/ToolCard.vue'

it('点击卡片触发 select 事件', async () => {
  const wrapper = mount(ToolCard, { props: { tool: { id: 'bmi' } } })
  await wrapper.get('button').trigger('click')
  expect(wrapper.emitted('select')).toBeTruthy()
})
  • 组件测试要点：渲染 → 找元素（优先 role/text，别靠 class）→ 交互 → 断言结果；不测内部实现细节

3.2 给 AI 代码建护栏（本课程最核心的工程习惯） ​

AI 产出默认"能跑但不一定对"，合入前必须过流水线：

类型检查 → lint → 单测 → 构建 → 人工 review diff → 合并
  • 没有 CI 就本地跑，别跳过
  • 测试的价值不在"证明现在对"，而在"给未来改动兜底"——AI 时代尤其重要（行为护栏）
  • 生产实践：给工具函数/关键组件补单测；前端 e2e 用浏览器自动化（Playwright / Chrome DevTools MCP）走流程（登录/下单/搜索）

必会：写 stub/mock/spy 三件套示例；讲测试金字塔与"AI 产出 → 关卡"流水线。

4. CI/CD（L3） ​

4.1 GitHub Actions 完整示例（能抄） ​

yaml
# .github/workflows/ci.yml —— 完整三件套
name: CI
on:
  push:
    branches: [main]
    paths: ['packages/web/**', 'packages/server/**', 'pnpm-lock.yaml']  # paths 过滤
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }   # pnpm 11 要求 Node ≥ 22.13
      - name: Install pnpm
        run: npm i -g pnpm@11
      - name: Cache pnpm store          # 缓存：安装从 2 分钟 → 20 秒
        uses: actions/cache@v4
        with:
          path: ~/.local/share/pnpm/store
          key: pnpm-${{ hashFiles('pnpm-lock.yaml') }}
      - run: pnpm install --frozen-lockfile   # lockfile 一致性
      - run: pnpm lint
      - run: pnpm --filter web build
      - run: pnpm --filter server build
  • 矩阵：strategy.matrix.node-version 多版本并行验证
  • 密钥：走 GitHub Actions Secrets（如 secrets.JWT_SECRET），构建产物不含 .env——绝不打进镜像/产物
  • 部署注意：先推代码 → 服务器上 prisma db push（保留线上数据，见生产部署配置）
  • 回滚策略：能快速回滚上一版本 > 完美部署。某生产项目部署演进过：简单 rsync ↔ 原子切换（先 .staging 再 swap），最后选简单稳定方案——真实取舍样本

必会：默写一个带缓存 + paths 过滤的 workflow；讲密钥与回滚策略。

5. Monorepo 与协作（L3） ​

5.1 pnpm workspace 实操（命令 + 心智） ​

bash
pnpm --filter web dev                      # 只跑 web 包
pnpm --filter server add zod               # 只给 server 加依赖
pnpm --filter web run build --filter=...   # 依赖过滤（含依赖它的包）
pnpm install --frozen-lockfile             # CI 用：lockfile 不一致直接失败
  • 依赖隔离：每个包独立 node_modules，重复依赖硬链接到全局 store（省磁盘、版本隔离——A 包用 vue 3.5、B 包用 vue 3.4 互不干扰）
  • lockfile 心智：pnpm-lock.yaml 锁全量版本，保证 CI/本地一致；改了依赖必须提交 lockfile

5.2 turbo 增量缓存 ​

json
// turbo.json —— 未变更包跳过，产物缓存命中
{
  "pipeline": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "lint":   { "dependsOn": ["^build"] }
  }
}
  • 缓存键 = 输入文件 hash + 依赖产物；turbo build --force 强制重跑

5.3 AGENTS.md 范式（给 AI 的"项目宪法"） ​

本学习站根目录 AGENTS.md 是范例：项目概述/架构/命令/约定/坑，硬链接同步 CLAUDE.md（一处修改处处生效）。维护它属于 08 上下文工程：让 AI 第一次就写对，而不是反复返工。

必会：写出 pnpm --filter 常用命令；讲 turbo 缓存键原理；解释 AGENTS.md 每条约定对 AI 的意义。

6. 性能预算与监控（L3） ​

6.1 性能预算（CI 卡阈值） ​

js
// vite.config.ts —— 体积预算：超了构建报错
build: {
  chunkSizeWarningLimit: 500,
  rollupOptions: { output: { manualChunks } },
}
  • 配合 Lighthouse CI：lighthouse-ci 给 LCP/INP/CLS 设阈值，PR 超了不让合并——防止"慢慢变胖"

6.2 监控三件套 ​

ts
// 错误上报（Sentry 类）：sourcemap 还原 + 按版本聚合
import * as Sentry from '@sentry/vue'
Sentry.init({ app, dsn: import.meta.env.VITE_SENTRY_DSN, release: __APP_VERSION__ })

// 性能指标（RUM）：真实用户数据才是真相
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    report({ name: entry.name, value: entry.value })   // LCP/INP/CLS
  }
})
observer.observe({ type: 'largest-contentful-paint', buffered: true })
  • 日志：结构化 JSON + traceId（前端把 traceId 放进请求头，后端日志贯穿——联调排查靠它）
  • 发布灰度：静态资源 content-hash + 平滑切换，避免"新 HTML 配旧 chunk"白屏（衔接 05 章缓存）

必会：写体积预算配置；讲 RUM 与实验室指标的区别；设计"错误 + 性能 + 日志"三件套。

7. 面试高频题速答 ​

题速答要点
tree-shaking 为什么必须 ESM静态分析依赖图，CJS 运行时才知道导出
Vite dev/build 为什么不同dev 原生 ESM 不打包；build 要压缩/分割，用 Rollup/Rolldown
代码分割怎么决策路由懒加载 + 大依赖 vendor + 体积报告驱动
循环依赖 ESM vs CJSlive bindings 先行绑定 vs 运行时拷贝快照
测试金字塔怎么搭单测多快、e2e 少而关键路径
AI 代码怎么防回归类型/lint/单测/构建关卡 + review
monorepo 依赖隔离pnpm store 硬链接 + 每包独立 node_modules
为什么需要回滚预案发布失败恢复速度 > 部署完美度
性能预算怎么做CI 卡体积 + Lighthouse CI 卡 Web Vitals
