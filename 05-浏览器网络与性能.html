05 · 浏览器·网络·性能 ​

达标目标：链路与缓存到 L2，性能与安全到 L3。 一句话理由：AI 给你"看起来对的代码"，但性能、兼容、安全问题几乎只能靠你对浏览器机制的理解兜底——这是"能上线"判断力的重要一块。 学习建议：第 1 节"输入 URL 到首屏"是面试第一问，练到 10 分钟一气呵成。

1. 输入 URL 到首屏：完整链路（L2 必考） ​

1.1 分段详解 ​

① DNS 解析（域名 → IP）

  • 缓存层级：浏览器缓存 → 系统缓存 → hosts → 本地 DNS → 递归查询 → 迭代查询（根 → TLD → 权威）
  • dns-prefetch：提前解析（对跨域资源有效）；preconnect 更进一步（建 TCP）
  • DoH（DNS over HTTPS）：防窃听/污染

② TCP 连接（三次握手）

  • SYN → SYN+ACK → ACK；为什么不是两次（防止已失效的连接请求到达服务器建立幽灵连接）；不是四次（服务端 SYN+ACK 可合并一次）
  • 握手消耗一个 RTT；TLS 又加 1-2 个 RTT——所以 HTTPS 首次建连约 2-3 RTT

③ TLS 握手（HTTPS）

  • 证书校验（CA 链 + 域名 + 有效期）、客户端/服务端协商密钥
  • 一句讲清"为什么防中间人"：公钥加密 + 证书证明"这把公钥确实是服务器的"
  • TLS 1.3 把握手压缩到 1-RTT（0-RTT 有重放风险）

④ HTTP 请求：请求行（方法/路径/协议）+ 请求头 + 请求体；先查缓存（见第 3 节），命中直接返回

⑤ 服务器响应 → HTML 解析（构建 DOM）

  • 字节 → 字符 → token → 节点 → DOM 树
  • 遇 <script>：阻塞 HTML 解析（默认）；defer（HTML 解析完再执行，按序）vs async（下载完即执行，乱序）
  • 遇 <link rel=stylesheet>：阻塞渲染但不阻塞 HTML 解析（继续构建 DOM）
  • 小技巧：<script> 放 </body> 前或用 defer/async/module

⑥ 构建 CSSOM：CSS 是渲染阻塞资源（RenderTree 需要它）；CSS 越小越早越好

⑦ RenderTree → Layout → Paint → Composite

  • RenderTree = DOM + CSSOM 合并（去掉 display:none）
  • Layout（reflow）：计算几何（位置/尺寸）
  • Paint：绘制成像素（分层）
  • Composite：合成层合并输出屏幕（GPU 加速）

⑧ 首屏指标映射（能指出来就是深度）

指标覆盖链路
TTFBDNS+TCP+TLS+服务端处理（首字节到达）
FCP首段可见内容绘制
LCP最大内容元素（图片/文本块）绘制

1.2 加分点（面试爱听） ​

  • HTTP/2 多路复用解决了连接级队头阻塞，但 TCP 丢包仍有传输级队头阻塞 → HTTP/3（QUIC over UDP）解决
  • CDN 在 DNS（就近解析）、TCP（就近建连）、缓存（边缘命中）三层同时生效

必会：10 分钟一气呵成讲完整链路，能接住"这里缓存会怎样 / 这里 script 会阻塞吗"的追问。

2. 渲染管线与合成（L2） ​

2.1 五步渲染管线 ​

DOM + CSSOM → 样式计算（匹配规则，计算值）→ Layout（几何）→ Paint（绘制）→ Composite（合成）

2.2 三种更新路径（高频考点） ​

触发涉及阶段例子
reflow（重排）Layout + Paint + Composite改 width/height/margin/top、读 offsetWidth
repaint（重绘）Paint + Composite改 color/background
composite（合成）仅 Compositetransform/opacity
  • 为什么 transform/opacity 动画不卡：只走合成层，不触发 layout/paint，由 GPU 合成
  • 合成层：浏览器把某些元素提升为独立层（will-change/transform/video）；合成层过多反而占内存（will-change 别滥用）
  • 面试题：1000 个 DOM 更新为什么卡？→ 每次都触发 reflow + 重绘；优化：批量（DocumentFragment）、content-visibility、虚拟列表、读写分离

2.3 布局抖动（layout thrashing）与长任务 ​

js
// 坏：循环里读 offsetWidth（强制同步布局）又改样式（触发下一次）
for (...) { box.offsetWidth; box.style.width = x + 'px' }  // 每次循环都 reflow
// 好：先批量读、再批量写（读写分离）
  • 长任务（>50ms）：阻塞渲染与交互 → 影响 INP
  • 拆解：requestIdleCallback（空闲执行低优先级）、任务分片（MessageChannel/setTimeout 切块）、Web Worker（纯计算挪出主线程）
  • INP 的本质：从用户交互到页面响应的延迟，长任务/布局抖动是主因

必会：答"为什么 transform 不卡"；写读写分离示例；说清 reflow/repaint/composite 三路径。

3. 网络与缓存（L2） ​

3.1 HTTP 版本演进 ​

HTTP/1.1HTTP/2HTTP/3
连接每请求一个连接（或 keep-alive）多路复用（一个连接并发流）多路复用 + 无 TCP 队头阻塞
队头阻塞连接级 + 传输级仅传输级（TCP 丢包）基本消除（QUIC over UDP）
头部明文重复HPACK 压缩QPACK 压缩
建连慢快一点0-RTT

3.2 缓存体系（两层级 + 启发式） ​

强缓存（不发请求）：

Cache-Control: max-age=3600        # 相对时间
Cache-Control: immutable           # 内容不变
Expires（HTTP/1.0，用绝对时间，有坑）→ 被 max-age 取代

协商缓存（发请求，304 省体积）：

ETag: "abc123"（内容哈希）→ 请求带 If-None-Match
Last-Modified → 请求带 If-Modified-Since（秒级精度，不如 ETag 准）
  • 启发式缓存：响应没有 Cache-Control 时，浏览器按 Last-Modified 的 10% 估算新鲜期——所以生产接口务必显式给 Cache-Control
  • 优先级：Cache-Control > Expires > 启发式

3.3 缓存更新与发布（L3 核心坑） ​

  • 静态资源：文件名带 content-hash（app.abc123.js）→ 内容变、URL 变、天然失效
  • 新 HTML 配旧 chunk 白屏：HTML 不缓存（no-cache），资源强缓存+hash；发布时新 HTML 引用新 chunk——若发布流程中断导致 index.html 与 chunk 不一致就白屏（生产部署专门处理过）
  • 常见坑：接口被强缓存（用户拿到旧数据）；no-store 与 no-cache 语义混淆

缓存决策伪代码（L3，先想清楚再动手）：

问三个问题：
① 资源会变吗？        会 → network-first 或协商缓存；不会 → 强缓存
② 变了我能接受旧的吗？  能 → stale-while-revalidate；不能 → network-first
③ 是带 hash 的静态资源吗？是 → cache-first（强缓存一年）
生产铁律：HTML 永远 no-cache；带 content-hash 的静态资源强缓存；API 按业务定

Service Worker 三种缓存策略（能写）：

js
// cache-first（静态资源）：命中缓存直接返回，不联网
// network-first（HTML/关键接口）：先联网拿新的，失败才用缓存
// stale-while-revalidate（次要资源）：先回缓存，后台静默刷新
self.addEventListener('fetch', (e) => {
  if (e.request.method !== 'GET') return
  const url = new URL(e.request.url)

  if (url.pathname.endsWith('.js') || url.pathname.endsWith('.css')) {
    // cache-first
    e.respondWith(caches.match(e.request).then((hit) => hit || fetch(e.request)))
  } else if (url.pathname === '/') {
    // network-first —— HTML 不缓存，避免"新 HTML 配旧 chunk"白屏
    e.respondWith(fetch(e.request).catch(() => caches.match(e.request)))
  }
})

3.4 CORS 与 Cookie ​

  • 预检（preflight）：跨域 + 非简单请求（自定义头/非 GET/POST/Content-Type 非表单三类）→ 先 OPTIONS 探询
  • 简单请求：GET/POST/HEAD + 表单 Content-Type + 无自定义头
  • Access-Control-Allow-*：Origin/Headers/Methods/Credentials
  • Cookie 安全四件套（结合 08 章认证）：HttpOnly（防 JS 读）、Secure（仅 HTTPS）、SameSite（防 CSRF：Strict 同站 / Lax 顶层导航可带 / None 需 Secure）、Max-Age

3.5 资源加载优化 ​

  • preload：立即下载（关键资源，如 LCP 图片/字体）
  • prefetch：空闲下载（下一跳资源）
  • preconnect：提前建连；dns-prefetch：提前解析
  • 代码分割 + 懒加载（衔接 04 章）：首屏只加载需要的 chunk

必会：画强缓存/协商缓存分支；答 preflight 何时触发；写缓存决策三问。

4. 存储与安全（L3） ​

4.1 存储选型 ​

存储容量特点适用
Cookie~4KB随请求自动携带会话标识（HttpOnly）
localStorage~5-10MB同步、持久、同源非敏感配置/缓存
sessionStorage同左标签页隔离、关闭即清临时会话数据
IndexedDB大（GB 级）异步、结构化、事务大文件/离线数据
Cache API大配合 Service Worker离线缓存（PWA）

4.2 XSS（跨站脚本） ​

三种：反射型（URL 参数注入）、存储型（存入 DB 再渲染）、DOM 型（前端 JS 把不可信内容插入 DOM）

防御（纵深）：

  1. 输出转义（框架默认）
  2. DOMPurify 洗白不可信 HTML（生产常用）
  3. CSP（见 4.4）——最有效的兜底
  4. Cookie HttpOnly（防窃取 token）

4.3 CSRF（跨站请求伪造） ​

  • 原理：Cookie 自动携带 → 受害者浏览器对已登录站点发出伪造请求
  • 防御：SameSite=Lax/Strict（首选）、CSRF token（服务端校验）、双重提交、自定义头校验
  • 面试点：为什么 SameSite 能防（跨站请求不自动带 Cookie）；XSS 与 CSRF 的区别（XSS 偷信任、CSRF 借身份）

4.4 CSP（内容安全策略） ​

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  connect-src 'self' https://api.example.com;
  img-src 'self' data: https:;
  • 最小化原则：能不放就不放；script-src 是关键（压 XSS 的根）
  • 与 XSS 的关系：即使注入成功，CSP 也挡住脚本执行/外连
  • 部署注意：先用 Content-Security-Policy-Report-Only 观察，再强制

4.5 其他安全头 ​

X-Frame-Options: DENY（防点击劫持）、HSTS（强制 HTTPS）、X-Content-Type-Options: nosniff、混合内容（HTTPS 页里 http 子资源）要清

必会：各举一个 XSS/CSRF 攻击与防御；写一份最小化 CSP 并解释每条；讲 Cookie 四件套各防什么。

5. 性能工程（L3） ​

5.1 Core Web Vitals 优化清单 ​

LCP（<2.5s）：首屏加载

  • 图片：WebP/AVIF + loading=lazy（但 LCP 图别 lazy）+ preload
  • 去掉渲染阻塞 CSS/JS；压缩/缓存；SSR/静态化首屏
  • TTFB 优化（服务端/CDN/缓存）

INP（<200ms）：交互响应

  • 减少主线程长任务（拆任务/懒加载 JS）
  • 避免布局抖动（读写分离）；事件防抖/节流
  • 组件级：虚拟列表、content-visibility

CLS（<0.1）：布局稳定

  • 图片/广告/嵌入提前占位（aspect-ratio/固定尺寸）
  • 字体 font-display: swap（有 CLS 代价，权衡）；避免动态插入影响布局的内容

5.2 排查工具流（L3 必会） ​

Lighthouse（体检出报告）
  → Performance 面板（录制，看长任务/强制布局/耗时）
  → Memory 快照对比（找内存泄漏：操作前后各拍一张）
  → Network（瀑布图：看阻塞、未压缩、缓存 miss）
  → Coverage（未用代码 → 该懒加载）

5.3 内存泄漏排查（衔接 01 章） ​

流程：录制堆快照 → 重复"触发→释放" → 对比找只增不减对象 → Retainers 看保留路径 → 定位代码。常见：未清理定时器/监听、闭包误用、分离 DOM 引用。

js
// 排查实操（DevTools）
// 1. Memory 面板拍一张堆快照（baseline）
// 2. 反复执行"打开 → 关闭"某个操作 N 次
// 3. 再拍一张，选"对比（Comparison）"
// 4. 找 Delta 为正、只增不减的对象（Detached DOM 节点、闭包里的对象）
// 5. 点开对象 → Retainers 看保留路径 → 定位"谁还持有它"
// 6. 常见修复：
//    clearInterval(timer) / removeEventListener('click', handler)
//    onUnmounted(() => { clearInterval(t) })   // Vue 组件卸载时清理

5.4 RUM 与监控（L3） ​

  • 真实用户监控（RUM）：采集线上真实 LCP/INP/CLS（实验室测不出真实网络）
  • 上报：PerformanceObserver + 采样上报 + 按版本/地区聚合
  • 与 04 章性能预算衔接：CI 卡实验室指标，RUM 卡线上体验

必会：写 LCP/INP/CLS 三件套优化清单各 3 条；讲排查工具流；会做内存泄漏对比快照。

6. 面试高频题速答 ​

题速答要点
输入 URL 到首屏DNS → TCP → TLS → 请求 → DOM/CSSOM → RenderTree → Layout → Paint → Composite（可展开 10 分钟）
强缓存 vs 协商缓存不发请求 vs 发请求拿 304；Cache-Control/ETag
为什么 transform 不卡只走合成层（GPU），不触发 layout/paint
HTTP/2 vs HTTP/3多路复用解决连接级队头阻塞；QUIC 解决传输级
缓存更新怎么不白屏HTML no-cache + 资源 hash 强缓存 + 平滑发布
XSS/CSRF 区别与防御偷信任 vs 借身份；转义+DOMPurify+CSP vs SameSite+token
LCP 慢的 3 个原因服务器慢（TTFB）、渲染阻塞资源、图片加载慢
长任务怎么拆requestIdleCallback / 分片 / Worker / 懒加载
