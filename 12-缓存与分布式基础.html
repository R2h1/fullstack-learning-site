12 · 缓存与分布式基础 ​

达标目标：L2 概念能讲透 / L3 能落地能判断。 一句话理由：缓存是性能的第一杠杆，但"穿透/击穿/雪崩"是生产事故三兄弟；分布式概念决定你能不能接住"如果数据量 ×100"。 衔接：与 05 章（HTTP 缓存）、09 章（幂等）、11 章（数据库）联动。

1. 缓存体系（L3） ​

1.1 缓存位置分层 ​

浏览器缓存 → CDN → 反向代理（Nginx）→ 应用内存 → Redis → DB
层速度一致性典型
浏览器最快最弱（用户端）Cache-Control（衔接 05 章）
CDN快边缘过期静态资源/图片
Nginx快代理缓存响应缓存
应用内存快单实例进程内 LRU
Redis中全局一致热点数据/计数/会话

设计原则：离用户越近越快，但一致性越难——每一层都要想"要不要缓存、怎么失效"；能缓存静态就缓存静态，动态数据才下探。

1.2 三大经典问题（L3 必答，含代码） ​

① 缓存穿透（查不存在的数据）

ts
// 问题：查 id=999999（不存在）→ 缓存永远 miss → 每次都打 DB
// 恶意攻击：构造大量不存在的 key → DB 被打穿

// 解法 1：缓存空值（短 TTL）
const data = await redis.get(`user:${id}`)
if (data === null) {                              // 注意：区分"没缓存"与"缓存了空"
  const user = await db.find(id)
  if (!user) { await redis.set(`user:${id}`, 'NULL', 'EX', 60); return null }  // 空值缓存 60s
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 3600)
  return user
}
// 解法 2：布隆过滤器（请求前先判断"可能存在"，不存在直接返回）

② 缓存击穿（热点 key 过期瞬间）

ts
// 问题：秒杀商品 key 过期 → 一瞬间 10 万请求全部 miss → 打爆 DB
// 解法：互斥锁——只放一个请求去重建，其余等待
const data = await redis.get(`hot:${id}`)
if (data) return data
const lock = await redis.set(`lock:${id}`, '1', 'EX', 5, 'NX')   // NX=只有不存在才设置（拿锁）
if (lock) {
  const fresh = await db.find(id)                // 只有拿到锁的这一个去查 DB
  await redis.set(`hot:${id}`, JSON.stringify(fresh), 'EX', 3600)
  await redis.del(`lock:${id}`)
  return fresh
}
await sleep(50)                                   // 没拿到锁：等一下再读缓存
return getHot(id)
// 解法 2：逻辑过期（缓存永不过期，值里带过期时间，异步重建）

③ 缓存雪崩（大面积同时过期）

ts
// 问题：一批 key 设置了相同过期时间 → 同时失效 → DB 瞬间高负载
// 解法 1：过期时间加随机
await redis.set(key, value, 'EX', 3600 + Math.random() * 600)
// 解法 2：多级缓存（Redis 挂了还有本地缓存兜底）
// 解法 3：熔断降级（DB 扛不住时直接返回旧数据/默认值）

必会：讲三兄弟场景 + 各两种解法；写互斥锁击穿代码；写空值缓存穿透代码。

1.3 缓存一致性（Cache-Aside） ​

主推 Cache-Aside（旁路缓存）：

读：先查缓存 → miss 查 DB → 写缓存 → 返回
写：先更新 DB → 删缓存（下次读时重建）

更新顺序的坑（L3 必答）：

顺序问题
先删缓存再写 DB写库期间有请求查到旧数据重建缓存 → 脏缓存
先写 DB 再删缓存删缓存失败会短暂脏 → 延迟双删 / 消息队列兜底
ts
// 先写库再删缓存（主流）+ 失败重试
async function updateUser(id, data) {
  await db.user.update(id, data)
  try { await redis.del(`user:${id}`) }
  catch { await mq.send('cache_invalidate', { key: `user:${id}` }) }  // 失败进 MQ 兜底
}
  • 面试点：缓存一致性没有银弹，读多写少场景 Cache-Aside + 最终一致够用；强一致就别上缓存
  • 最终一致兜底：延迟双删（写库后等一小段再删一次）/ MQ 驱动失效

必会：画 Cache-Aside 读写流程；讲两种更新顺序的坑与兜底；说"强一致就别上缓存"。

1.4 Redis 深度（L3） ​

结构场景例子
string计数/缓存INCR 登录失败次数、缓存值
hash对象字段用户资料（改一个字段不整取）
list队列/时间线LPUSH+BRPOP 简单队列
zset排行榜ZADD score member——生产排行榜可类比
set去重/交集共同关注
ts
// 限流：固定窗口（衔接 09 章）
const count = await redis.incr(`rate:${ip}`)
if (count === 1) await redis.expire(`rate:${ip}`, 60)
if (count > 100) return 429
  • 过期策略：惰性删除（读时发现过期才删）+ 定期删除（抽样）
  • 生产注意：key 带业务前缀（acme:user:42）；大 key 拆分；maxmemory + 淘汰策略（allkeys-lru）
  • 面试点：Redis 单线程为什么快（内存 + IO 多路复用 + 避免锁）；单线程 = 大 key/慢命令会阻塞所有请求（慎用 KEYS）

必会：讲 zset 排行榜；写 Redis 限流；讲单线程快的原因与大 key 风险。

2. 分布式基础（L2 概念 / L3 能谈） ​

2.1 CAP（L2 必答） ​

C 一致性 / A 可用性 / P 分区容错
  • P 必选（网络分区不可避免）→ 实际是 CP vs AP 的取舍
  • 一致性级别：强一致 / 最终一致 / 读己之写（会话内）
  • 面试回答套路："多数业务选 AP + 最终一致 + 幂等兜底"——分区时保证可用，恢复后靠补偿/幂等收敛
  • 反例：余额扣减要 CP（宁可不可用不能错账）；Feed/点赞 AP 足够

2.2 幂等与重试（衔接 09 章，分布式视角） ​

  • MQ 消费端为什么必须幂等：ack 超时 → 重投 → 同一消息被消费多次
ts
// 消费端幂等：业务唯一键 + DB 唯一约束兜底
async function consume(msg) {
  try {
    await prisma.order.create({ data: { requestKey: msg.id } })  // 唯一约束
  } catch (e) {
    if (e.code === 'P2002') return            // 已处理过，跳过（幂等）
    throw e                                    // 真错误 → 重投
  }
  // ... 执行业务
}
  • 铁律：没有幂等就没有可靠重试；重试要有上限 + 指数退避

2.3 消息队列概念（L2/L3） ​

生产者 → Broker（队列）→ 消费者
  • 核心机制：ack（消费成功才删消息）、重投（失败/超时重发）、死信队列（多次失败进死信，人工处理）
  • 什么场景需要 MQ：
    • 削峰（秒杀写请求排队）
    • 解耦（订单创建 → 发通知/扣库存，异步不阻塞）
    • 异步化（耗时操作后台跑）
  • 什么时候不需要（L3 判断）：同步能搞定、无削峰需求 → 别上 MQ（多一个组件 = 多一类故障）

2.4 水平扩展（L3 能谈） ​

  • 无状态服务随便扩（多实例 + LB）
  • 有状态是瓶颈：session（→ Redis 共享）、DB（→ 读写分离/分片）、文件（→ 对象存储）
  • 扩展阶梯：垂直（加配置）→ 读写分离（主写从读）→ 缓存（Redis）→ 分库分表（最后手段，别早做）
  • 面试点：能说"先缓存后分片，分片是最后手段"就是经验

必会：讲 CAP 取舍套路；写 MQ 消费幂等代码；讲"要不要 MQ"判据；画扩展阶梯。

3. 面试高频题速答 ​

题速答要点
缓存穿透不存在的数据打 DB；布隆过滤器/缓存空值
缓存击穿热点 key 过期瞬间；互斥锁/逻辑过期
缓存雪崩大面积同时过期；随机 TTL/多级缓存/降级
缓存一致性Cache-Aside 写库后删缓存；延迟双删/MQ 兜底
更新顺序坑先删后写会脏；先写后删失败要兜底
Redis 为什么快内存 + IO 多路复用 + 单线程无锁
大 key 风险阻塞单线程所有请求；慎用 KEYS
CAP 怎么答P 必选，CP vs AP；多数 AP + 最终一致 + 幂等
MQ 消费为什么幂等重投重复消费；唯一键兜底
什么时候不需要 MQ同步够用、无削峰需求
扩展顺序缓存 → 读写分离 → 分片（最后手段）
