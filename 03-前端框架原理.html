03 · 前端框架原理（Vue 3 为主 + React 对照） ​

达标目标：L2 硬门槛——所精框架原理讲 15 分钟经得起追问，另一框架能讲 5 分钟对照；L3——状态架构与性能决策。 一句话理由：框架能写出"能跑"的页面，但"为什么更新不生效 / 为什么卡 / 为什么状态串扰"只能靠原理定位。 示例项目是 Vue 3 栈（企业主流），主讲 Vue（含完整实现图景），React 作对照。

1. Vue 3 响应式全链路（L2 硬门槛） ​

1.1 一句话原理 ​

Proxy 拦截读取与写入 → 读取时收集依赖（track）、写入时触发更新（trigger）→ 依赖是 effect。

1.2 最小可运行实现（能默写，讲原理直接画） ​

js
let activeEffect = null
const bucket = new WeakMap() // target -> Map<key, Set<effect>>

function track(target, key) {
  if (!activeEffect) return
  let deps = bucket.get(target) ?? new Map()
  let set = deps.get(key) ?? new Set()
  set.add(activeEffect)
  deps.set(key, set)
  bucket.set(target, deps)
}

function trigger(target, key) {
  bucket.get(target)?.get(key)?.forEach((fn) => fn())
}

function reactive(obj) {
  return new Proxy(obj, {
    get(target, key) { track(target, key); return Reflect.get(target, key) },
    set(target, key, value) {
      const ok = Reflect.set(target, key, value)
      trigger(target, key)
      return ok
    },
  })
}

function effect(fn) {
  activeEffect = fn
  fn()            // 首次执行 = 收集依赖
  activeEffect = null
}

1.3 调度器与批处理（生产级，追问高频） ​

真实 Vue 不是"改一次立刻更新"——effect 回调进任务队列，去重 + 批量，在微任务里统一 flush：

修改 state → trigger → 把 effect 加入 job 队列（Set 去重）
  → 同步代码跑完 → 微任务中 flush 队列 → 一次更新 DOM
  • 这就是 nextTick 的底层：同步改 N 次 state，DOM 只更新一次；nextTick 回调在 flush 之后执行
  • 好处：性能（避免重复渲染）+ 一致性（一次渲染看到一致状态）
  • 追问点：为什么用 Set 去重（同一 effect 多次触发只跑一次）；为什么微任务（保证同步代码全部执行完）

1.4 必须讲清的点（每点都是面试题） ​

问题答案
为什么 reactive 解构丢响应性？解构只发生一次取值，之后是原始值；Proxy 拦截只在 obj.count 访问时生效。解法 toRefs（每属性转 ref）
ref 为什么存在？基础类型无法被 Proxy 拦截，包成 { value } 对象；模板自动解包，setup 里要 .value
computed 为什么"懒"？依赖变化且被读取时才重算，结果缓存；watch 是依赖变化立即执行回调（副作用）
shallowRef 干嘛用？大对象不做深度代理，性能优化（配合 triggerRef 手动触发）
为什么 Proxy 优于 defineProperty？能监听新增/删除属性、数组索引/length；不用递归预遍历（Vue2 的局限）

1.5 watch 的 flush 时机（L3 细节） ​

  • flush: 'pre'（默认）：DOM 更新前，组件更新前——读不到更新后的 DOM
  • flush: 'post'：DOM 更新后（watchPostEffect），能读最新 DOM
  • flush: 'sync'：同步执行（慎用，性能差）
  • watch 默认是惰性的（不立即执行）；watchEffect 立即执行一次并自动收集依赖

必会：默写 reactive/effect 最小实现；讲 track/trigger + 批处理/nextTick 链路；答 1.4 表里 5 个追问。

2. 渲染器与更新（L2） ​

2.1 虚拟 DOM 与 patch 流程 ​

render() → vnode 树 → 对比新旧 vnode（patch）
  → 按 vnode.type 分发（组件/元素/文本/Fragment）
  → 只更新差异部分（props、children、事件）
  • 为什么有 vnode：直接操作 DOM 昂贵（layout/paint），vnode 是"描述结构"的 JS 对象，对比出最小变更
  • props 更新：diff 新旧 props 对象，只 patch 变化的
  • 事件更新：Vue 缓存事件（onClick 不重复创建），更新时整体替换事件对象（避免重复绑定）

2.2 diff 与 key（高频） ​

  • 同层比较：只比同层节点，不跨层（假设"同一层结构变化"）
  • key 的作用：有 key 时按 key 匹配可复用节点（移动而非重建）；无 key 按索引推断——索引错位 → 组件状态串扰（经典 bug：删除列表中间项后，后面所有项的输入框内容错位）
  • 快速 diff：头部/尾部贪心匹配 + 剩余部分用 key 建索引 + **最长递增子序列（LIS）**求最小移动次数
  • 面试能讲："O(n) 复用 + LIS 算最少移动"即可，不要求默写算法

简版 patchChildren（理解 key 的作用，L2 能写）：

js
function patchChildren(oldChildren, newChildren, container) {
  // 无 key：按索引对比（错位会误复用）
  // old: [A, B, C]  new: [A, C, B] → 中间项会复用错对象
  const keyedOld = new Map(oldChildren.map((c) => [c.key, c]))
  for (const newChild of newChildren) {
    const old = keyedOld.get(newChild.key)   // 有 key：精确找到旧节点
    old ? patch(old, newChild, container)    // 复用并更新
       : mount(newChild, container)          // 新节点插入
  }
}

没有 key 时 diff 按索引配对：删除列表中间项后，后面所有项"错位复用"，各自状态（如输入框内容）跟着错位——这就是"必须给稳定 key"的原因。

2.3 编译优化（Vue3 快的关键，L2） ​

  • patchFlag：编译时给动态节点打标记（动态文本/动态 class/动态 props/需要全量 diff），更新时只看标记部分
  • 静态提升：静态节点（无动态绑定）提升到渲染函数外，只创建一次，更新直接复用
  • 事件缓存：onClick 绑定不重复创建
  • 结论：模板写法比手写 render 快（模板能静态分析，手写 render 无法分析动态性）
  • 面试点：为什么 v-if/v-for 同一元素上优先级有坑（Vue3 中 v-if 优先于 v-for，与 Vue2 相反）

必会：讲 vnode/patch 流程；写简版 keyed diff；讲 patchFlag/静态提升为什么让模板快。

3. Composition API 与组件架构（L2/L3） ​

3.1 为什么要有 Composition API ​

  • mixin 三坑：命名冲突（两个 mixin 同名方法）、来源不明（哪个 mixin 提供的？）、隐式依赖（mixin 内部引用了什么外部状态？）
  • composable（组合式函数）：显式返回、来源清晰、可传参可复用
ts
// useFetch 模式（面试常让写）
function useFetch<T>(url: Ref<string>) {
  const data = ref<T | null>(null)
  const error = ref<Error | null>(null)
  const loading = ref(false)
  watch(url, async () => {
    loading.value = true
    try { data.value = await (await fetch(url.value)).json() }
    catch (e) { error.value = e as Error }
    finally { loading.value = false }
  }, { immediate: true })
  return { data, error, loading }
}

3.2 组件通信全清单（必答） ​

方式用途
props / emits父子显式数据流
v-modelprops + emits 的语法糖（modelValue + update:modelValue）
provide/inject跨层级；全局配置/组件库；缺点是隐式依赖
Pinia跨组件共享状态（全局）
attrs透传未声明 props（如 class/事件）
ref 暴露父组件调用子组件方法（defineExpose）

3.3 生命周期（父子顺序，必背） ​

创建：父 setup → 子 setup → 子 onMounted → 父 onMounted
更新：父 beforeUpdate → 子 beforeUpdate → 子 updated → 父 updated
卸载：父 beforeUnmount → 子 beforeUnmount → 子 unmounted → 父 unmounted

面试点：为什么"父 onMounted 里拿子 DOM"会拿不到（子先挂载完）；onUnmounted 里清定时器/监听（结合 01 章内存泄漏）。

3.4 Vue Router / Pinia 要点 ​

  • 路由：动态 import 懒加载（切 chunk）、导航守卫（全局/路由级/组件内）做认证——生产级 router/index.ts 是范本
  • Pinia：defineStore、setup store vs option store、storeToRefs 解构保响应性（对应 1.4 的 toRefs 场景）

必会：写 useFetch 组合式函数；背组件通信全清单；背生命周期父子顺序；讲 mixin 三坑。

4. React 对照（能讲 5 分钟） ​

4.1 Fiber：可中断渲染 ​

  • 旧版问题：递归渲染不可中断，长更新卡主线程
  • Fiber 方案：渲染拆成可中断的工作单元（fiber 节点链表），配时间片（约 5ms 检查）与优先级（lane），实现并发
  • 双缓冲：current 树 + workInProgress 树，commit 时一次性切换——用户永远看到一致状态
  • render phase vs commit phase：render 可中断、可重复（为什么 render 里不能有副作用）；commit 不可中断

4.2 Hooks 原理 ​

  • Hooks 按调用顺序存在 fiber 节点的链表中 → 不能条件调用（顺序错位 = 状态串扰）
  • stale closure：闭包捕获旧值；依赖数组 = 让 effect 拿到最新值
  • useEffect vs useLayoutEffect：前者异步（commit 后），后者同步（commit 前，防闪烁）
  • setState 批处理：React 18 自动批处理（事件/定时器内也批）；传函数 setCount(c => c+1) 避免依赖旧值

Hooks 为什么不能条件调用（链表示意）：

js
// 每次渲染，hooks 按调用顺序存入 fiber 的链表
// 第 1 次渲染：useState(0) -> useState('') -> useEffect(fn)   [A, B, C]
// 某次渲染 if 条件让第 2 个 hook 没执行：                      [A, C]
// 第 3 次渲染恢复：useState(0) 后的第 2 次调用会取到 C 的位置 → 状态错位！
// 所以 React 报错：Hooks must be called in the same order every render

useEffect 简版心智（依赖数组 = 让闭包拿到最新值）：

js
function useEffect(fn, deps) {
  const prevDeps = hook.state // 存在 fiber 节点上
  if (!prevDeps || !deps || deps.some((d, i) => d !== prevDeps[i])) {
    hook.state = deps
    queueMicrotask(fn) // 真实实现在 commit 后执行，支持清理与可中断
  }
}

4.3 性能优化三件套的真相 ​

  • memo：props 引用不变才跳过渲染；配合 useCallback/useMemo 才有意义
  • useMemo：计算昂贵才用，别给所有派生值套（缓存本身有开销）
  • useTransition / useDeferredValue：低优先级更新可被打断 → 输入框不卡
  • 面试点：useCallback 不是"性能银弹"——依赖数组写错反而引入 bug

必会：讲 Fiber 可中断 + 双缓冲 + render/commit；画 Hooks 链表并解释"为什么不能条件调用"；讲 stale closure。

5. SSR / SSG 选型（L3） ​

方案适用代价
CSR（纯前端）应用型、登录后内容SEO 差、首屏依赖 JS
SSR（Nuxt/Next）需要 SEO / 首屏快服务器渲染开销、状态水合（hydration）
SSG（构建时预渲染）内容型、变化少（文档/博客）内容变化需重新构建
ISR/混合两者兼顾复杂度上升

判断：本学习站（内容型）该用 SSG；登录后内容的 SaaS 产品用 CSR 合理——能给出这样的判断即 L3。

必会：给任意页面做 SSR/CSR/SSG/ISR 选型并说出代价。
