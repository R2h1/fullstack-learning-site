11 · 数据库深度 ​

达标目标：L2 硬门槛——索引/事务能讲透；L3——EXPLAIN 实操与 ORM 选型判断。 一句话理由：接口快慢、数据对不对、并发下乱不乱，全在数据库这一层；AI 能帮你写查询，但"索引怎么建、事务怎么用、表怎么设计"必须是你自己的判断。 示例用 Prisma 5 + MySQL（企业级数据库），全程对照 prisma/schema.prisma。

1. 索引原理（L2 硬门槛） ​

1.1 B+ 树为什么是默认索引结构 ​

B+ 树特点：
  ① 叶子节点存全部数据 + 按序相连（链表）→ 范围查询友好
  ② 非叶子只存"键"（不存数据）→ 扇出高（一页能装很多键）→ 树矮
  ③ 树矮 = 查询磁盘 IO 次数少（3 层 B+ 树 ≈ 3 次 IO）
  • 对比：Hash 索引适合等值查询但不支持范围/排序；B+ 树等值 + 范围 + 排序通吃
  • 聚簇 vs 非聚簇：
    • 聚簇：表数据按主键物理有序存储（SQLite/MySQL InnoDB 主键索引）；主键索引直接拿数据，不用回表
    • 非聚簇：索引叶子存主键/指针，查非索引字段要回表（二次 IO）

1.2 联合索引与最左前缀（必考） ​

sql
-- 联合索引 (a, b, c)
CREATE INDEX idx_a_b_c ON t (a, b, c);

-- 能用到：
WHERE a = 1              -- ✅ 只用 a
WHERE a = 1 AND b = 2    -- ✅ a,b
WHERE a = 1 AND b = 2 AND c = 3  -- ✅ 全用
WHERE a = 1 AND c = 3    -- ⚠️ 只用 a（b 断档，c 用不上）

-- 用不上：
WHERE b = 2              -- ❌ 没从 a 开始
  • 为什么：联合索引按 (a,b,c) 字典序组织，跳过前缀就不知道往哪走
  • 面试变体：a=1 AND b IN (2,3) AND c=4 → a 用索引、b 用索引、c 用不上（IN 之后断档）

1.3 哪些查询用不上索引（L3 必答） ​

sql
WHERE name LIKE '%xx'          -- ❌ 前导通配符
WHERE YEAR(created_at) = 2025  -- ❌ 函数包裹列
WHERE phone = 13800138000      -- ⚠️ 隐式类型转换（字符串列 vs 数字）
WHERE a + 1 > 10               -- ❌ 列参与运算

1.4 EXPLAIN 读法（L3 实操） ​

sql
EXPLAIN SELECT * FROM books WHERE author = 'xxx';
-- SQLite: EXPLAIN QUERY PLAN ...

-- 关键列：
-- type：const（主键/唯一命中）> eq_ref > ref > range > index > ALL（全表扫）
-- rows：预估扫描行数（越小越好）
-- extra：Using index（覆盖索引，不用回表 ✓）
--        Using where / Using filesort（排序没用索引）/ Using temporary（临时表）

慢查询优化套路：EXPLAIN 看 type/rows → 确认是否走了预期索引 → 加索引/改查询 → 再 EXPLAIN 对比 rows 下降

1.5 覆盖索引（L3） ​

sql
-- 索引 (author, title)：查询只要这两列 → 索引里全有 → Using index，不用回表
SELECT author, title FROM books WHERE author = 'x';
  • 场景：高频查询的列全部塞进索引，用索引空间换回表 IO

必会：讲 B+ 树三特性；写最左前缀判断；背"用不上索引"四类；读 EXPLAIN 关键列。

2. 事务与并发（L2 硬门槛） ​

2.1 ACID（能逐个讲防什么） ​

特性含义防什么
A 原子性全部成功或全部回滚半成功状态
C 一致性事务前后约束成立脏数据/约束破坏
I 隔离性事务间互不干扰并发相互影响
D 持久性提交后不丢宕机丢失

2.2 隔离级别矩阵（必背） ​

级别脏读不可重复读幻读
读未提交❌❌❌
读已提交✅❌❌
可重复读✅✅❌（MySQL 靠间隙锁基本防住）
串行化✅✅✅
  • 脏读：读到另一个事务未提交的数据（可能被回滚）
  • 不可重复读：同一查询两次，行数据变了（更新导致）
  • 幻读：同一范围两次，行数变了（插入/删除导致）——SQLite 默认可重复读 + 单写者，天然规避写冲突
  • 面试点：不可重复读 vs 幻读的区别（改一行 vs 多一行），很多人混

2.3 锁与死锁（L2/L3） ​

  • 共享锁（读）/ 排他锁（写）：读写互斥、读读共存
  • 行锁 vs 表锁：行锁并发高但有死锁风险；表锁简单但并发差
  • 死锁：A 持锁 1 等锁 2，B 持锁 2 等锁 1 → 互相等待
  • 预防 = 固定加锁顺序（都先锁 id 小的）；DB 兜底检测死锁回滚一方

2.4 乐观锁 vs 悲观锁（L2 必答，含代码） ​

sql
-- 悲观锁：SELECT ... FOR UPDATE（事务内锁住行）
BEGIN;
SELECT * FROM inventory WHERE id = 1 FOR UPDATE;  -- 别人读这行要等
UPDATE inventory SET stock = stock - 1 WHERE id = 1;
COMMIT;
sql
-- 乐观锁：版本号条件更新（影响行数 = 0 说明被并发改过）
UPDATE inventory
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;      -- 期望版本号
-- 若影响 0 行 → 冲突，重试或报错
乐观锁悲观锁
冲突少✅ 推荐锁开销浪费
冲突多重试成本高✅ 直接排队
场景读多写少（购物车数量）写冲突激烈（库存扣减）

2.5 事务生产规范（L3） ​

  • 短事务：尽快提交，长事务占锁拖垮并发
  • 不在事务里做网络请求：放大锁持有时间（一个慢 HTTP 请求 = 锁挂几分钟）
  • SELECT ... FOR UPDATE 有代价，能不用不用（先问"真需要锁吗"）
  • 事务边界写清楚（服务层，别散在 ORM 回调里）

必会：背隔离级别矩阵；区分不可重复读 vs 幻读；写乐观锁/悲观锁；讲死锁预防。

3. ORM 与 Prisma（L3，对照生产实现） ​

3.1 Prisma 核心 ​

prisma
// schema.prisma（生产风格）
model Book {
  id        Int      @id @default(autoincrement())
  userId    Int
  title     String
  status    String   @default("want")
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id])

  @@index([userId, status])        // 联合索引：按用户+状态查书单
  @@unique([title, author])        // 唯一约束：幂等兜底（衔接 09 章）
}
  • schema 即类型（prisma generate 产出 TS 类型）
  • 迁移：db push（直接同步，快速迭代）vs migrate（版本化迁移，生产规范）；快速迭代阶段用 push + 保留线上数据策略，企业规范用 migrate
  • 面试点：能讲"push vs migrate 的取舍"（push 简单但不可回滚，migrate 有历史可回滚）

3.2 N+1 查询（ORM 最常见性能坑，必答） ​

ts
// ❌ N+1：先查 100 个用户，再循环里每个查一次书 → 101 条 SQL
const users = await prisma.user.findMany()
for (const u of users) {
  await prisma.book.findMany({ where: { userId: u.id } })  // 100 次查询！
}

// ✅ 一次 JOIN 取出
const users = await prisma.user.findMany({ include: { books: true } })  // 1-2 条 SQL
  • 本质：循环里发查询 = 查询次数随数据量线性增长，慢查询 + DB 压力翻倍
  • 排查：日志里 SQL 条数异常；用 relationLoadStrategy: 'join' 或 include 一次取

3.3 数据库选型：SQLite vs MySQL vs PostgreSQL（L3 必会） ​

SQLiteMySQL（企业默认）PostgreSQL
形态单文件嵌入式服务端服务端
并发写弱（单写者锁库）强（MVCC + 行锁）强（MVCC 多写者）
全文检索FTS5InnoDB FULLTEXT / 配 ESpg 全文 + GIN 索引
JSON一般JSON 类型（8.0+）强（jsonb + 索引）
生态零运维生态最成熟、运维资料最多特性最强、团队要求高
何时用个人项目/单机起步/原型企业默认选型强 jsonb/复杂全文/特定扩展时
  • 判断逻辑（L3）：个人项目/单机单写者 → SQLite 够用（起步最快）；企业级默认 MySQL——生态成熟、云厂商托管普及、招聘市场主流；需要 jsonb、复杂全文检索、GIN 索引等特定能力 → PostgreSQL
  • 面试点：能讲"为什么企业默认 MySQL 而不是 SQLite/PG"（并发写、运维生态、托管服务、招人成本）

必会：写带联合索引 + 唯一约束的 Prisma 模型；讲 N+1 与解法；讲 SQLite vs MySQL vs PG 的选型判断。
